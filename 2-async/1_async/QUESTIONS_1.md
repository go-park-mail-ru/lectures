# Мини-квиз: горутины и каналы

По коду: `1_goroutines`, `1_goroutines/i_ptr`, `2_chan`, `2_chan_2`.

---

### 1. Что напечатают горутины?

```go
const goroutinesNum = 7

func main() {
	for i := 0; i < goroutinesNum; i++ {
		// i := i
		go func() { // А если go < 1.22?
			fmt.Println(i)
		}()
	}
	time.Sleep(time.Second)
}
```

- A. Всегда `0 1 2 3 4 5 6` в каком-то порядке — у каждой горутины своё `i`
- B. На Go **&lt; 1.22** почти наверняка семь семёрок; с **1.22** — `0..6` в любом порядке
- C. Паника: `i` уже не существует, когда горутина стартует
- D. Компилятор не даст замкнуть `i` без `i := i`

<details>
<summary>Ответ</summary>

**B.**

До Go 1.22 цикл переиспользовал **одну** переменную `i`. Горутина захватывает её по ссылке, а к моменту `Println` цикл уже дошёл до `7`. Отсюда трюк с `i := i` — локальная копия на итерацию.

С Go 1.22 у каждой итерации своё `i`, костыль больше не нужен. Порядок печати всё равно любой: планировщик не обещает FIFO.
</details>

### 2. Указатели в цикле. В чём подвох?

```go
var ptrs []*int
for i := 0; i < 3; i++ {
	ptrs = append(ptrs, &i)
}
fmt.Println(*ptrs[0], *ptrs[1], *ptrs[2])
```

- A. Всегда `0 1 2`
- B. Всегда `3 3 3`
- C. До 1.22 — `3 3 3` (один `i` на всех); с 1.22 — `0 1 2`
- D. Паника: `i` ушла со стека, разыменование нельзя

<details>
<summary>Ответ</summary>

**C.**

Та же история, что в вопросе 1, только без горутин. `&i` до 1.22 — адрес **одной** ячейки; после цикла там `3`. С 1.22 каждая итерация создаёт новую переменную, адреса разные, значения `0 1 2`.

В `range` та же ловушка: `&i` внутри `for i, v := range ...` до 1.22 указывал на одну переменную цикла.
</details>

### 3. Кто кого ждёт?

```go
ch1 := make(chan int)

go func(in chan int) {
	val := <-in
	fmt.Println("get", val)
}(ch1)

fmt.Println("before")
ch1 <- 42
fmt.Println("after")
```

Что про этот код правда?

- A. `before`, сразу `after`, потом когда-нибудь `get 42` — send не блокируется
- B. `before`, затем send ждёт читателя; после хендшейка `after` и `get 42` (в любом порядке)
- C. Deadlock: main не может писать, пока горутина не дочитает
- D. `get 42` всегда печатается строго до `after`

<details>
<summary>Ответ</summary>

**B.**

Небуферизованный канал — это **синхронизация**, не почтовый ящик. `ch1 <- 42` встанет, пока другая горутина не сделает `<-ch1`. После передачи main и горутина бегут параллельно: `after` и `get 42` могут поменяться местами.

`time.Sleep` в примере — не синхронизация, а «подождать глазами». Настоящий барьер здесь — сам канал.
</details>

### 4. Раскомментировали вторую запись

```go
ch1 := make(chan int)

go func(in chan int) {
	val := <-in
	fmt.Println("get", val)
}(ch1)

ch1 <- 42
ch1 <- 100500 // вот это
```

- A. Горутина прочитает оба значения по очереди
- B. `100500` перезапишет `42` в канале
- C. Deadlock: читатель уже вышел, писать больше некому
- D. Паника: в небуферизованный канал нельзя писать дважды

<details>
<summary>Ответ</summary>

**C.**

Первый send проходит. Горутина прочитала одно число и закончилась. Второй `ch1 <- 100500` на небуферизованном канале **навсегда** ждёт читателя. В `main` это `fatal error: all goroutines are asleep - deadlock!`

Буфер `make(chan int, 1)` спасёт только **одну** лишнюю запись. Вторую — снова дедлок, если никто не читает.
</details>

### 5. `range` по каналу. Что если забыть `close`?

```go
in := make(chan int)

go func(out chan<- int) {
	for i := 0; i <= 10; i++ {
		out <- i
	}
	// close(out)  // закомментировали
}(in)

for i := range in {
	fmt.Println("get", i)
}
fmt.Println("done")
```

- A. Напечатает `0..10` и `done` — range сам поймёт, что писать больше некому
- B. Напечатает `0..10` и повиснет на `range`: ждёт следующее значение вечно
- C. Паника после последнего числа
- D. Компилятор не пропустит `range` по открытому каналу

<details>
<summary>Ответ</summary>

**B.**

`for range ch` читает, пока канал **не закроют**. Закрывать должен тот, кто пишет (у вас как раз `chan<- int` — только запись).

Без `close` после `10` цикл в main так и останется в `<-in`. Горутина-генератор уже умерла → дедлок.

`ok` в `v, ok := <-ch` — тот же сигнал: `ok == false`, когда канал пуст и закрыт.
</details>

### 6. Закрытый канал: читать можно, писать нельзя

```go
ch := make(chan int, 2)
ch <- 1
close(ch)

v1 := <-ch
v2 := <-ch
ch <- 2
```

- A. `v1=1`, потом паника на втором чтении
- B. Паника на `close`: буфер ещё не пуст
- C. `v1=1`, `v2=0`, паника на `ch <- 2`
- D. `v1=1`, `v2=1`, запись пройдёт — в буфере есть место

<details>
<summary>Ответ</summary>

**C.**

`close` не выкидывает буфер: сначала отдадут `1`. Потом канал пуст и закрыт → чтение даёт **zero value** (`0` для `int`), без паники. Сколько угодно раз.

Запись в закрытый — всегда паника, даже если `cap` ещё «как будто есть». Повторный `close` — тоже паника. `close(nil)` — тоже паника.
</details>

### 7. Трюковый бонус: буфер на ноль и nil

```go
a := make(chan int, 1)
a <- 42
fmt.Println("sent a")

b := make(chan int, 0)
b <- 42
fmt.Println("sent b")

var c chan int
c <- 42
fmt.Println("sent c")
```

Что напечатается, если запускать как есть (один `main`, без других горутин)?

- A. `sent a`, `sent b`, `sent c`
- B. Только `sent a`, потом deadlock на `b`
- C. `sent a` и `sent b`, deadlock на `c` — nil это «бездонный» канал
- D. Паника на `c <- 42`

<details>
<summary>Ответ</summary>

**B.** Только `sent a`, затем deadlock.

`make(chan int, 1)` — буфер на один: send не ждёт читателя, пока есть место.

`make(chan int, 0)` — это **тот же** небуферизованный канал, что `make(chan int)`. Без читателя — дедлок. До `c` программа не дойдёт.

Если бы `c` выполнилось: `var c chan int` это `nil`. Чтение/запись в nil-канал **блокируются навсегда**, не паникуют. На этом держатся `select {}` и `<-blockNil` — вечный sleep без таймера.
</details>
